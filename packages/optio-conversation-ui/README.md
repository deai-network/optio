# optio-conversation-ui

Engine-neutral **conversation widget** for [optio](https://github.com/deai-network/optio) tasks. One React widget renders a live chat transcript for a headless agent session and drives it (send / interrupt / approve permissions / switch model / upload + download files) through the optio widget proxy — for **both** the `claudecode` and `opencode` engines.

This package replaces the engine-specific `optio-claudecode-ui`. A single registration serves both engines; each task self-declares its wire protocol.

## Install

```sh
pnpm add optio-conversation-ui
```

Peer deps: `react >=18`, `react-dom >=18`, `antd >=5`.

## Usage

Register the widget once in your host app (alongside `optio-ui`):

```ts
import { registerConversationWidget } from 'optio-conversation-ui';

registerConversationWidget();
// or, when the host has no antd ConfigProvider of its own and you want the
// widget to own a light/dark toggle:
registerConversationWidget({ ownTheme: true });
```

It registers for `ui_widget = "conversation"`. Each task carries its engine in `widgetData.protocol` (`"claudecode"` or `"opencode"` — injected automatically by `optio-claudecode` / `optio-opencode`), and the widget dispatches to the matching view. You do **not** specify the engine at registration.

## Features

- Streamed chat transcript (replay + live) with optimistic local echo.
- Steering while the agent works (claudecode, via the view's `onSteer`): the busy input bar is `[Send when ready | Interrupt and send]` (Enter / ⌘/Ctrl-Enter) beside the red Interrupt; a message the agent has not taken yet is a dashed "Queued" bubble with **Send now**; an interrupted answer keeps its text with a jagged bottom edge, followed by one muted "⏹ Interrupted by you" row. The input bar always renders one fixed-width multi-action send button (owner ruling 2026-09-14, so it never resizes between idle and busy): idle, closed, or a view without `onSteer` shows just **Send**; busy and steerable swaps in `[Send when ready | Interrupt and send]`, and the main half reverts to Send once idle again.
- Session end and resume (claudecode, Fix 19, owner rulings 2026-09-15): a session that ends mid-turn (stopped, suspended or restarted while Claude thinks, streams or runs a tool) shows one muted "⏹ Interrupted: session ended" row, in the same place and style as "⏹ Interrupted by you"; the answer it cut off keeps the text streamed so far and renders like an interruption (jagged edge, trailing "…"), and a running tool row is stopped. Messages still queued when it ended are re-queued automatically on resume, in their original order, and delivered when Claude is ready: their bubbles stay queued (never "Not delivered"), and nothing Claude had already taken is sent twice.
- Send now delivers up to a message (Fix 13b, owner ruling 2026-09-15): `onSteer: (text, attachments, upTo?) => Promise<boolean>` takes an optional third argument; a queued bubble's own **Send now** click passes its own id as `upTo`, so with three messages queued, clicking Send now on the 2nd delivers the 1st and 2nd and leaves the 3rd queued (the bar's own Send when ready / Interrupt and send calls never pass `upTo`). `ClaudeCodeView` turns it into `POST /steer {text:"", upTo}`.
- Interrupt gives immediate feedback (manual-test finding, owner ruling 2026-09-14): `onInterrupt: () => Promise<boolean> | void` resolves whether the request reached the listener. While in flight the button keeps its "Interrupt" label and shows an active spinner instead, ignoring further clicks (Fix 18, owner ruling 2026-09-15: a changing label made the buttons jump); on success it returns to normal (the "⏹ Interrupted by you" row still comes from the listener's `x-optio-interrupt`, as before); on `false` or a rejection it shows "Interrupt failed — retry." through the same error slot Send/Send now use. A void-returning handler (the other engines, unchanged) is treated as immediate success. Interrupt is rendered as a vultus `ActionButton` (danger variant) at a fixed width, same pattern as the send button above; the `data-testid="conversation-interrupt"` now sits on that fixed-width wrapper span, one level above the vultus button itself (`[data-action-id="interrupt"]`).
- Tool-call and permission cards (approve / deny) when the task runs a permission gate.
- Model switching (when the task enables `show_model_selector`).
- File upload (📎) and one-click file download (agent emits `[name](optio-file:relpath)`), when the task enables `show_file_upload` / `file_download`.
- Markdown rendering with GFM, LaTeX math (KaTeX), Mermaid diagrams, and themed code blocks.
- Optional opt-in light/dark theming (`ownTheme`).

## Consumer requirements

Because the widget renders rich markdown, the host bundler must handle:

- **CSS imports** — the widget imports `katex/dist/katex.min.css`. Ensure your bundler can import CSS from `node_modules`.
- **KaTeX fonts** — served from the `katex` package; make sure they resolve at runtime.
- **Mermaid** — client-only; render the widget in the browser, not during SSR.
- **antd theme** — wrap your app (or the widget) in an antd `ConfigProvider` if you want a non-default theme, or use `registerConversationWidget({ ownTheme: true })`.

See `src/AnswerBlock.tsx` for the authoritative list.

## Exports

- `registerConversationWidget(opts?)`, `ConversationWidget` — the widget + its registration.
- `AnswerBlock` — the standalone markdown/answer renderer.
- `reduceClaudecodeEvent`, `reduceOpencodeEvent`, `historyToChatItems`, `initialChatState`, `ChatItem`, `ChatState` — the engine-neutral chat model and per-engine reducers, for embedding outside the default widget.
  - Tool items (`kind: 'tool'`) may carry `callId` (the call's wire id), `result` (its output, trimmed), `startedAt` / `endedAt` (epoch ms; the view shows a live elapsed counter until `endedAt` is set), `background` (a backgrounded shell command) and `taskId` (its background task id). All are optional and set by the claudecode reducer only.
  - A tool item's `status` may also be `'stopped'`: stopped rather than completed or failed (a background task stopped or killed, or a call still running when the session closed or a resumed run replaced it). It renders as finished, not failed.
  - `reduceClaudecodeEvent(state, ev, seq, now?)`: `now` (epoch ms, default `Date.now()`) is the clock used only until the stream has shown a user/assistant timestamp; pass it for deterministic replays and tests.
  - Steering fields (all optional, claudecode reducer only): user items `queued` (a "Send when ready" message the agent has not taken yet, pinned at the bottom of the transcript) and `queueId` (the id optio gave the message — the CLI's own `uuid`, since Fix 13a — kept once it is taken, re-keyed in place by a later `x-optio-requeued`); assistant items `interrupted` (cut off by the operator); activity items `muted` (a quiet one-line note, e.g. an undelivered message, instead of the harness `System:` bubble), `system` (Fix 14, owner ruling 2026-09-15: set only for a harness `System:` echo, so the view can tell it apart from an untimed background-task/upload-notice row sharing the same non-muted branch — see Message timestamps below) and, only for a note made from a `command_lifecycle` cancellation (see below), `queueId` (the id it replaced, so a later requeue can find it); user/assistant/error/activity items also carry `timestamp` (see Message timestamps below). The reducer maps the listener's `x-optio-queued`, `x-optio-taken` and `x-optio-interrupt` events onto `queued`/`queueId`/`interrupted`/`muted`, plus the view's own local echo. `x-optio-queued` only sets `queued: true` while the reducer's own `busy` still reads `true` at the moment it arrives — the listener also emits it for `interrupt_and_send`'s own steered text, but only once that turn has already ended (`busy` false by then), and that text must show as a plain unconfirmed bubble, never the pinned "Queued … Send now" one (review of fix 8, final-review M3, finding 1: clicking Send now there would `POST /steer` with empty text and interrupt the turn the message itself just started).
  - Lifecycle-driven queued bubbles (Fix 13b, owner ruling 2026-09-15, per `cli-queue-lifecycle.md`): for a user item with an id (a queued bubble's `queueId`, or a local echo's), the CLI's own `command_lifecycle` events move it by uuid instead of matching echo text. `'started'` for that uuid takes the bubble to this point in the transcript (the take point), same as an echo would; an `isReplay` echo carrying the same uuid (`ev.uuid`, top-level) then only confirms it and backfills a still-unset `timestamp` — it never creates a second bubble, so a fold's later combined echo (several text blocks, only the last one's uuid) adds no duplicates for the earlier ones. `'cancelled'`, `'discarded'` or `'refused'` for a bubble not re-queued turns it into a "Not delivered" note, exactly as at session end, but carrying the old id as `queueId`; `x-optio-requeued` (`{id, new_id}`) re-keys a still-queued bubble in place, or — when the CLI's own `'cancelled'` (the session-end cancel sweep) reached the buffer first, as it does for a message a resumed run re-sends (Fix 19's `requeue_undelivered`, after `x-optio-resumed`'s own `restoreQueuedTail` has already restored it to queued under the old id) — restores the note it had already made back into a queued bubble under the new id, carrying its original send timestamp through, if it had one. A conversation with no uuids at all emits none of these (the CLI: "commands enqueued without a uuid emit no lifecycle events"), so the pre-13b FIFO text match is the fallback in every branch, unchanged. A queued bubble or its "Not delivered" note both count as the pinned tail for ordering purposes (`isPinned` in `chat.ts`): new content, and a later-taken sibling, always lands in front of either kind, never past it.
  - Review of Fix 13b (2026-09-15), four fixes:
    - **Trim trailing whitespace on every text-match path** (the single-block match and each fold block, both direct matches and the fallback creating a fresh bubble from an echo): Fix 13a appends a blank line to a message sent while busy, but the queued/local bubble's own text (and a legacy, uuid-less conversation's fallback matching) never carries it — an untrimmed compare missed the match, leaving the original stuck queued and rendering a visible duplicate with the trailing blank line.
    - **A "Not delivered" note's `queueId` eventually clears** (`isPinned` stops matching it) once no further `x-optio-requeued` can plausibly still restore it: at the next CLEAN turn end (never the ABORTED-interrupt branch, which a same-turn "Send now up to" resend may still be pending against), and unconditionally at `x-optio-resumed` / `x-optio-closed`. Before this, a note nothing ever requeued stayed pinned at the very bottom for the rest of the conversation. Also, `command_lifecycle` `'started'` now confirms (clears `local` on) a plain, never-queued local echo too, not only a queued one — otherwise a later abort `'cancelled'` for the same uuid (an aborted turn also reports `'cancelled'` for the message that started it) wrongly matched an already-delivered idle send as undelivered.
    - **`'started'` clears a bubble's pre-existing `timestamp`** before the taking echo can backfill it (Fix 4: the taking echo's wire time replaces the send time). Live, a queued bubble already carries the widget's own local send time (`x-optio-local-user`); when `'started'` takes it ahead of its echo (a fold's last message; "Send now up to"'s re-sent message), the old backfill-only-if-unset rule let that local time win forever, diverging from replay (which never had one to begin with).
  - Session end and resume (Fix 19, owner rulings 2026-09-15): `x-optio-interrupt` with `by: 'session'` renders like an operator interrupt (the in-flight bubble `interrupted`, running non-background tool rows `stopped`, the CLI's own interrupt artefacts swallowed and its final text landing in front of the row) with the row text `INTERRUPTED_SESSION_ENDED` (`chat.ts`, "⏹ Interrupted: session ended"); unlike an operator interrupt, whatever result ends that turn keeps this rendering (no too-late undo, no error row, no second copy of the answer), and an operator interrupt already in flight keeps "⏹ Interrupted by you". `x-optio-partial` (`{id, text}`) is the text message `id` had streamed when the session ended without its final assistant event: it becomes that message's text and marks it `interrupted`. `x-optio-resumed` may carry `requeued: string[]`, the ids the resumed run re-sends: those bubbles stay queued, and a "Not delivered" note already made for one turns back into its queued bubble, which the following `x-optio-requeued` re-keys. A "Not delivered" note that does not pin (made at session end, or unpinned at a turn end or session boundary) keeps its message id as activity `requeueId`, so a later `x-optio-requeued` still restores it, at the bottom where queued bubbles are pinned. `dropUndelivered(items, keep?)` takes the ids to keep queued.
  - Message timestamps (owner request 2026-09-14, extended 2026-09-14 to `System:` rows — manual-test finding 3): user, assistant, error and non-muted activity items may carry an optional `timestamp` (epoch ms). The view renders it as a small grey time under the bubble (`HH:MM` for a message from today, else a short date — plus the year if not this year — then `HH:MM`; the full local date/time is the hover title), via the pure `formatMessageTime(timestamp, now)` in `src/messageTime.ts` (the view passes the current time; the reducer never reads the clock). Absent when no time is known (e.g. a still-queued bubble in a replay) — never invented. The claudecode reducer fills it from the wire: a user item gets its own event's `timestamp`; a queued "Send when ready" shows the view's local-echo send time live, replaced by the taking echo's own wire timestamp once Claude takes it; a harness `System:` echo (e.g. "you have been resumed", a deliverable notice) becomes a non-muted activity item carrying that same echo's own wire timestamp. Muted notice rows (an operator interrupt, an undelivered message) and background-task rows never carry one. Other engines' reducers don't set it, so their items simply show no time.
  - Fix 14 (owner ruling 2026-09-15, manual-test finding): a `System:` activity row (`system: true`) is styled more like a user message — the same bottom-right corner radius as a user bubble (`USER_BUBBLE_RADIUS` in `ConversationView.tsx`, also used by the two user bubbles themselves) and its time label right-aligned the same way a user bubble's is. Its position, colours and text styling are otherwise unchanged: the row still centers itself in the transcript. A background-task/upload-notice row (no `system` flag) keeps today's fully-rounded, centered rendering.
  - Assistant start-end interval (Fix 12, owner ruling 2026-09-14: a streamed message needs its own interval, not one borrowed instant): an assistant item's `timestamp` is now its START, and a new optional `endTimestamp` (epoch ms) is its END — the LAST wire `assistant` event seen for that message (what `timestamp` used to hold before this fix; a streaming delta carries neither). The view shows `formatMessageTimeInterval(start, end, now)` in `src/messageTime.ts`: "HH:MM - HH:MM" when start and end fall in different local minutes, a single "HH:MM" when they don't (each side dated exactly as `formatMessageTime` would date it alone); the hover title is `formatMessageTimeIntervalFull(start, end)`, the full local start and end (or just the end when there is no start). Nothing renders while `endTimestamp` is unset — the same "never invented" rule as every other item's `timestamp` — `timestamp` alone changes nothing visible. The claudecode reducer resolves `timestamp` once, when a message's bubble is first created, in priority order: (1) the listener's `x-optio-message-start` synthetic event (`{id, ts}`, matched by message id) — an exact stamp taken by the server the instant the message started, so live and replay show the identical value; (2) failing that, if the message's first (rendered) content block is a `thinking` narration block, that block's own completing wire time; (3) failing that, `lastEventAt` as it stood just BEFORE this message's first wire event — the previous user/assistant event, an approximation, not exact; (4) failing all three (no prior wire event at all — the very first message of a conversation replayed with no marker), no start. `endTimestamp` has no such chain: it is simply overwritten by every assistant wire event seen for the message, so it always ends up as the last one.
